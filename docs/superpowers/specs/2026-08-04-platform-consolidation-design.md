## 1. Проблема и цель

Платформа накопила работающие, но разрозненные приложения: `/p/okr` (без своего
хранилища, read-only Plane), `/p/hours` (JSON-файл на Docker-volume), база знаний
`kb.bbm.academy`, презентации в `bbm/outputs/` (частью на Vercel), Payload CMS для
сайта. Принцип SSOT спроектирован (PRD, KB-дизайн), но на практике не работает:
команда живёт одновременно в `team.yaml`, Payload-коллекции Team, `hours.json`,
Mattermost, Plane и Zitadel — синхронизация ручная. Финансовый учёт (приоритет
владельца) в такой среде строить нельзя.

Цель: перевести оперативные данные на единое ядро в БД, дать единую точку ввода
(админка за SSO), запустить пропагацию истины во все системы, включить Гермеса в
базу знаний, систематизировать наполнение KB и инженерную дисциплину.

Это **зонтичный дизайн**: он фиксирует архитектурные решения и декомпозицию.
Каждый эпик §13 проходит свой цикл (issue → при необходимости своя спека →
дизайн-гейт → «го» → TDD → ревью → приёмка) по `.claude/skills/task-cycle/SKILL.md`.

### Целевой портфель приложений (ревизия 2026-08-24-f)

Портал — **внутренняя корпоративная рабочая среда BBM**: место, где живут
оперативные данные и внутренние приложения. Лаунчер `/p` и админка `/p/admin` —
каркас этой среды, а не CRUD над парой таблиц. Целевой состав (владелец,
2026-08-24; порядок не является приоритетом):

- учёт часов (`/p/hours`) и OKR (`/p/okr`) — уже живут;
- финансы / внутренний бухгалтерский учёт (эпик 5, #115);
- внутренние презентации (`/p/decks`, эпик 8, #118);
- CRM;
- управление задачами (сегодня — Plane; глубина интеграции/замещения — по
  своему discovery);
- поиск и подбор команды;
- запуск проектов;
- калькуляторы и рабочие инструменты;
- связка с внутренней коммуникацией (Mattermost).

Пункты без номера эпика — целевые модули без начатого дизайна: каждый входит в
портал через собственный продуктовый цикл (ревизия -b: модель данных — после
продуктового дизайна) и встаёт модулем монолита по ADR-002. Часть портфеля
пересекается с фазами 8–9 PRD (проекты, вклады, витрина) — их продуктовый
контур остаётся в PRD. Здесь фиксируется требование к каркасу: информационная
архитектура лаунчера и оболочки админки и **контракт подключения модуля**
(пункт в лаунчере + ресурсы в админке) проектируются от этого портфеля, а не от
первых двух ресурсов — предмет спеки #311.

### Ядро `core`

Таблицы Payload живут в своей БД `cms` (схема `public`; адаптер вызван без
`schemaName`) — и остаются там. Ядро получает **отдельную БД `platform`** в том
же Postgres-контейнере, со схемой `core` внутри (ревизия 2026-08-04-b; закрыт
major ревью PR #109 — исходная редакция «по той же `DATABASE_URL`» противоречила
PRD §7.3). Приложение получает вторую строку подключения
(`PLATFORM_DATABASE_URL`); off-site бэкап обязан дампить обе БД. Слой —
**drizzle**: прямой зависимостью проект его пока не имеет (он внутри
Payload-адаптера db-postgres), поэтому `drizzle-orm`/`drizzle-kit` добавляются
явно, с пином, совместимым с версией внутри Payload; drizzle-kit смотрит только
в БД `platform`. Миграции `core` — собственный пайплайн отдельно от
payload-овского.

**Модель данных — продуктовая работа (ревизия 2026-08-04-b):** таблицы каждого
приложения разворачиваются после его продуктового цикла (брейншторм → дизайн →
спека с acceptance-сценариями), а не переносом MVP-структур; миграция
`hours.json` идёт после продуктового дизайна `/p/hours` (#124). Целевые
сущности ядра:

- `member` — участник BBM: первичный ключ — суррогатный id (slug уже существует
  в `team.yaml`); email `@bbm.academy` — атрибут с уникальным индексом
  (канонический идентификатор входа — KB-дизайн §2 решение 3; PK из него не
  делаем: email плохо переживает переименования и федеративный вход из
  DS-контура). Плюс имя, роль, статус (active/inactive), таймзона. Наполняется
  разовой миграцией из `hours.json` + `team.yaml`.
- `membership` — участие в круге/проекте. Полная модель Circle из PRD не
  разворачивается заранее (YAGNI), поля ей не противоречат.
- `event_log` — append-only журнал изменений (D-025; структура Contribution —
  D-005); hash chain добавляется позже без смены смысла.
- `outbox` — строки пропагации: цель, payload, статус, счётчик попыток.
- Таблицы `/p/hours` (периоды, записи, ставки) — участники через FK на `member`;
  `hours.json` после миграции остаётся замороженным архивом.

Границы модулей (`.dependency-cruiser.cjs`) расширяются: модуль не импортирует
внутренности чужого модуля и не трогает чужие таблицы напрямую.

## 5. Бэкенд (API-слой монолита)

Бэкенд платформы — серверная часть Next.js-монолита (Node.js-процесс) плюс
worker-процесс для фоновой работы. Он **не выносится в отдельно деплоящийся
API-сервис**: исходный PRD (фаза 5, D-017) планировал отдельный Core Service,
но ADR-002 заменил это модульным монолитом; право выделения модуля в отдельный
сервис по критериям ADR-002 §3 сохраняется (кандидаты — Access Sync по периметру
токенов, финансы по итогам discovery). Устройство:

- **Модуль владеет своим слоем данных.** Каждый платформенный модуль
  (`src/lib/<module>` / `src/modules/<module>` — по сложившейся структуре) держит
  доменную логику и drizzle-репозиторий к **своим** таблицам схемы `core`; наружу
  отдаёт типизированный публичный интерфейс. Чужие таблицы напрямую не трогает —
  граница машинно держится dependency-cruiser (§11).
- **Два способа вызова.** Серверные компоненты и server actions зовут модуль
  напрямую (in-process, без HTTP). HTTP-поверхность — route handlers
  `/api/p/<module>/*` — заводится только там, где есть клиентский потребитель
  (интерактивные экраны, админка); это не публичный API наружу.
- **Контракты — zod-схемы модуля**: одна схема валидирует вход handler-а и
  типизирует клиента (data provider админки ест её же).
- **Авторизация в каждом handler-е**: Zitadel-сессия + claim; UI-запреты
  удобство, границей доверия не являются.
- **Внепроцессная работа** (обработчик outbox, забор Zoom): отдельный
  compose-сервис `worker` из того же образа приложения — вне жизненного цикла
  веб-запросов; детали — в эпике 3.

## 6. Единая админка `/p/admin`

- Refine как тонкий CRUD-каркас: только `@refinedev/core` + роутер; их
  auth/data-пакеты не используются.
- Data provider — самописный, поверх route handlers из §5 (отдельного REST-слоя
  нет и не нужно).
- Вход — тот самый Zitadel-гейт `/p/*` + claim-гейт «админ платформы» (роль в
  Zitadel). UI-запрет — удобство; реальная авторизация — в серверных
  обработчиках (§5).
- Первые ресурсы: `members`, `hours` (правки участников/периодов переезжают из
  `/p/hours/admin` — снимается env-allowlist `HOURS_ADMIN_EMAILS` в пользу
  claim-гейта), дальше — финансы.
- Оболочка, навигация и контракт подключения модуля проектируются от целевого
  портфеля приложений (§4, ревизия -f), не от первых двух ресурсов; первые
  ресурсы — проверка контракта на живых жильцах. Спека каркаса — #311.

## 7. Пропагация (Access Sync)

Цепочка на примере «появился участник»:

1. Ввод в `/p/admin` → транзакция в `core` (`member` + строки `outbox` + `event_log`).
2. Обработчик outbox проецирует по целям: Zitadel (учётка), Mattermost
   (приглашение), Plane (приглашение), Payload Team (upsert editorial-записи →
   сайт пересоберётся имеющимся repository_dispatch; приёмник — issue `bbm-public-website#109`), `bbm-kb`.
3. Звено KB: GitHub App (расширение установки существующего site-dispatch App на
   `bbm-kb`, право `contents:write`) обновляет регенерированный
   `ssot/facts/team.yaml` с шапкой «GENERATED из портала — руками не править».
   **Не прямым пушем в `main`**: деплой KB требует `needs: [build, pr-guard]`,
   прямой коммит уронит `pr-guard` и остановит деплой — механика: ветка + PR от
   App + automerge (или явное исключение GENERATED-путей в `pr-guard`; выбор — в
   эпике 3). Дальше существующий CI собирает Fumadocs → `tools-prod-tw`.
4. Гермес получает обновление своим git-pull (`kb-pull.sh`) — бесплатно.

Одновременно с разворотом мастерства **выводится из эксплуатации встречный
CI-джоб `propagate-payload.yml` в `bbm-kb`** (`ssot/` → Payload): Access Sync
становится единственным писателем в Payload Team, иначе — двойная запись и цикл
`core → bbm-kb → CI → Payload`.

Требования к обработчику outbox (живёт в compose-сервисе `worker`, §5): выборка
`FOR UPDATE SKIP LOCKED`, экспоненциальный backoff, идемпотентность целей
(внешний ID на пару запись×система — повтор не создаёт дубликата). **Периметр
секретов**: админ-токены Zitadel/Mattermost/Plane, Zoom и ключ GitHub App живут
только в env worker-сервиса (host-only процедура) и недоступны веб-процессу с
его публичными поверхностями; централизация секретов (Infisical, D-027) — §14.

Деактивация участника — та же механика в обратную сторону (закрытие доступов).
Провал пропагации после ретраев = алёрт в Mattermost; статусы видны в админке.

Почему коммит в git, а не «KB тянет из API на билде»: у git-файлов `bbm-kb` три
потребителя (Fumadocs-билд, Гермес, AI-сессии команды с `ssot/` в CLAUDE.md),
коммит кормит всех разом; билд KB остаётся самодостаточным; git-история
`team.yaml` — бесплатная летопись команды.

Создание рабочей почты при онбординге — цель Access Sync, но хостинг почты
`@bbm.academy` и его API — открытый вопрос (§14).

## 8. Финансовый модуль (рамка, не дизайн)

Отдельное приложение `/p/finance` с собственным discovery → спека → дизайн-гейт.
Зафиксированные требования к фундаменту:

- мультивалютность: суммы в минимальных единицах валюты (bigint), точность
  валютно-зависимая (RUB — копейки, BTC — сатоши);
- конвертации (в т.ч. через крипту) — связанные группы проводок с явными
  комиссиями каждого шага и курсом, зафиксированным на момент операции;
- проводки immutable (сторно вместо правок), двойная запись;
- связь с `member` и данными `/p/hours` (контекстные ставки, #103).

Ядро `core` схему финансов не предрешает.

## 10. Дизайн-система

- Единый UI-кит для `/p/*` и админки: токены (цвета, типографика, отступы) +

  workspace-конверсии (ADR-002 §4); решение принимается, когда сайт реально
  потребует общие токены, не раньше.

  запреты модулей): любой модуль может импортировать `src/ui`; `src/ui` не
  импортирует ни один модуль. Заводится вместе с аналогичным правилом для `core`.
