# Канон задачника — как формулируется задача

Задачник репо — **GitHub Issues** `bbm-academy-org/bbm-portal` (CLAUDE.md); Plane
`BBMP-*` — организационный слой, не этот канон. Правила ниже — перенос образца
ds-platform (инвентаризация #127) под наши лейблы, борд и `task-cycle`.

Действует **на новые issue** с момента утверждения владельцем; существующие
переоформляет задача 7.2, а не задним числом. Канон описывает **формулирование**;
жизненный цикл (план → «го» → TDD → ревью → приёмка → мерж) остаётся за
`.claude/skills/task-cycle/SKILL.md`, ветки и порты — за `parallel-sessions.md`.
Язык: **заголовки секций и маркеры полей — английские и фиксированные** (их
парсит тулинг этапа 2), содержание — русское, как во всех наших issue.

## 1. Тело issue — фиксированный скелет

```markdown
**Source:** source:owner | source:spec | source:retro | source:agent

## Context

<Почему сейчас. Какую проблему закрывает. Ссылки: спека `docs/specs/…`,
ADR `docs/adr/…`, PRD, комментарий владельца с датой.>

## Scope

**In scope:**

- <конкретный deliverable>

**Out of scope:**

- <что задача НЕ закрывает и куда это уходит>

## Spec reference

<Спека/ADR + конкретный §. Если спека не нужна по gate'у task-cycle stage 1a —
пишется «нет спеки: <причина>», пустым это поле не бывает.>

## Acceptance criteria

- [ ] <наблюдаемо и проверяемо: команда, URL, статус, файл>

## Dependencies

**Blocked by:** #N — <технический rationale одной строкой>
**Blocks:** #M

## Notes

<Свободный текст. Сюда же сессии постят stop-state-комментарии (§5).>
```

Семантика и обязательность:

| Секция                | Что в ней                                                                                                                  | Обязательна          |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| `**Source:**`         | происхождение задачи; дублирует `source:*`-лейбл человекочитаемо. При расхождении **побеждает лейбл** — его читает тулинг  | всегда               |
| `Context`             | почему сейчас, какую боль закрывает, откуда взялось решение                                                                | всегда               |
| `Scope`               | **In** — deliverable'ы; **Out** — явно исключённое с адресом («уходит в #M»). Пустой Out — запах: значит границы не думали | всегда               |
| `Spec reference`      | спека/ADR/§ либо явное «нет спеки: …». Это фиксация gate'а stage 1a, а не украшение                                        | всегда               |
| `Acceptance criteria` | чек-лист наблюдаемых фактов. «Работает» — не критерий; критерий — что открыть/запустить и что увидеть                      | всегда, кроме `epic` |
| `Dependencies`        | человекочитаемое зеркало **нативного** графа (§3) + rationale ребра                                                        | если граф непуст     |
| `Notes`               | остальное; stop-state-комментарии живут комментариями, не правкой тела                                                     | по необходимости     |

Для `kind:fix` секция `Context` содержит воспроизведение: окружение, шаги,
ожидалось/получилось — иначе задача не берётся, а возвращается автору.
Для `epic` `Acceptance criteria` заменяется составом sub-issues: критерий эпика —
закрытые дети, отдельного чек-листа он не заводит.

**Заголовок** — свободный русский текст без Conventional-Commits-префикса: класс
задачи несёт `kind:*`-лейбл, дублировать его в title незачем.

## 2. Таксономия: `source:*` + `kind:*` + milestone

**Ровно один `source:*`** — происхождение, оно же ответ на вопрос «кто это
просил»: `source:owner` (просьба/решение владельца), `source:spec` (открыто из
спеки/ADR), `source:retro` (ретро, `/wrap`, разбор инцидента), `source:agent`
(инициатива агента — самая частая причина мусора в бэклоге, поэтому маркируется
явно).

**Ровно один `kind:*`** — `kind:feat` · `kind:fix` · `kind:chore` · `kind:docs`.

<!-- решение автора: четыре kind-лейбла вместо шести ds (bug/feature/chore/
refactor/docs/tooling) — потому что это ровно наши четыре префикса ветки
(`tools/dev/task-worktree.mjs` → BRANCH_TYPES) и типы Conventional Commits;
`refactor`/`tooling`/`ci`/`test` у нас и так сводятся к `chore`, отдельные
лейблы создали бы вторую, расходящуюся классификацию -->

Цепочка одна и без таблиц перевода: `kind:feat` → ветка `feat/<N>-<slug>` →
коммит `feat: …` → org Issue Type **Feature**. `kind:fix` → **Bug**,
`kind:chore`/`kind:docs` → **Task** (типы `Task/Bug/Feature` в организации уже
заведены, но не проставляются — обёртка этапа 2 деривует их из kind-лейбла).

**Milestone обязателен.** Milestone — долгоживущая тема, не спека и не эпик.
Сейчас заведена одна — «Консолидация платформы»; этап 2 создаёт постоянный
fallback **«Платформа: эксплуатация и упрочнение»** для процессных/эксплуатационных
задач, не попадающих ни в одну тему. Задача без milestone не создаётся.

**Структурные лейблы** (ортогональны таксономии, не заменяют её): `epic` —
зонтичная issue; `consolidation` — тематическая метка эпика консолидации,
уходит вместе с закрытием milestone. Эпик тоже несёт ровно один `source:*` и
ровно один `kind:*` — по классу своего deliverable.

**Запрещённый класс лейблов — статусные** (`blocked`, `ready`, `in progress`).
Статус берётся из нативного графа и борда; лейбл был бы вторым источником правды,
который рассинхронизируется первым.

**Судьба дефолтных лейблов GitHub** (решается в этапе 2, одним проходом):

| Лейбл                                              | Судьба                                                                                                               |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `bug` (3), `enhancement` (11), `documentation` (3) | мигрируют в `kind:fix` / `kind:feat` / `kind:docs` в задаче 7.2, затем удаляются — иначе два имени для одного класса |
| `duplicate`, `invalid`, `wontfix`                  | удаляются: это причины закрытия, а не свойства задачи (`gh issue close --reason not planned` + комментарий)          |
| `good first issue`, `help wanted`                  | удаляются: приватное репо с одним владельцем и агентами, внешних контрибьюторов нет                                  |
| `question`                                         | удаляется: вопрос владельцу — это не задача бэклога                                                                  |

Assignee по умолчанию `@me` — поле служит сигналом «кто-то взял», не распределением.

## 3. Канон связей — нативный граф, не проза

**Иерархия и зависимости живут в API GitHub, а не в тексте.** Проза «часть #117»,
«зависит от #130» связью **не считается** — её не видит ни борд, ни triage.

- **Родитель → ребёнок** — нативный sub-issue:
  `gh api --method POST repos/$OWNER/$REPO/issues/<P>/sub_issues -F sub_issue_id=<db-id ребёнка>`
  (эндпоинты берут **numeric DB id**, не номер: `gh api repos/$OWNER/$REPO/issues/<n> --jq .id`).
- **Зависимость** — `blocked_by`:
  `gh api --method POST repos/$OWNER/$REPO/issues/<B>/dependencies/blocked_by -F issue_id=<db-id блокера>`.
  Обратное ребро GitHub выводит сам — второй раз в другую сторону не проводить.
- Секция `Dependencies` в теле — **зеркало** графа для человека; расходится с
  графом — прав граф, тело правится.

**`blocked_by` = только техническая зависимость, с записанным rationale.** Ребро
значит «раньше физически нельзя», а не «сначала хотим другое»: приоритет
выражается порядком на борде и волнами хендоффов, никогда не рёбрами. Rationale
пишется **строкой в `Dependencies` заблокированной задачи** (`#N — почему`);
допустим комментарий на любой из двух задач, если контекст длиннее строки. Ребро
без rationale — provenance-orphan: triage его помечает, и это повод оспорить
ребро, а не считать фактом.

**Никогда не блокеры:** родитель/эпик, «связано с», «преемник», «сначала
обсудить». Иерархия ≠ зависимость.

**Открытие набора задач из спеки:** каждый ребёнок — нативный sub-issue родителя,
рёбра между детьми расставляются сразу, номера созданных issue дописываются
обратно в спеку. Набор не может приземлиться как N одновременно берущихся задач:
берущаяся — одна, голова критического пути, остальные заводятся заблокированными.
Кросс-репные дети (`bbm-public-website`) линкуются нативно (одна организация), но
**заводятся, а не реализуются** здесь — граница из CLAUDE.md.

## 4. Claim — задача взята = ворктри **И** статус

Спека консолидации §3, п. 10: сигналов занятости **два, обязательны оба**:

1. **ворктри** `.claude/worktrees/<N>` со своей веткой `<type>/<N>-<slug>`
   (`pnpm task:worktree <N>`) — создаётся **до первой правки файла**;
2. **статус `In Progress`** на борде Project 2 — ставится тем же движением.

Расхождение — само по себе нарушение канона, а не «мелочь»; его ловит
`backlog-triage`. Разрешение расхождения асимметрично:

- **ворктри есть, статуса нет** → правды больше у ворктри: работа физически идёт,
  борд отстал → **чинится борд**. Ворктри и ветка — факт файловой системы и
  origin, их нельзя «забыть по невнимательности» в обратную сторону.
- **статус есть, ворктри и ветки нет** → задача **не становится свободной
  автоматически**: агент помечает claim как протухший (с возрастом), решение
  освободить принимает лид/владелец. Чужой claim снимается людьми, не скриптом.

<!-- решение автора: SSOT-правило асимметрично — «ворктри как свидетельство

Выбранный порт dev-стенда фиксируется комментарием в issue (правило
`parallel-sessions.md`) — это часть того же claim'а: владелец открывает ссылку,
соседняя сессия видит занятый слот.

## 5. Stop-state-комментарий — фиксированная форма

Сессия, останавливающаяся на **не закрытой** задаче (конец сессии, блокер,
переключение приоритета), обязана оставить комментарий ровно такой формы:

```markdown
**Where I stopped:** <последний коммит / последняя успешная команда / где чтение оборвалось>
**What remains:** <конкретные шаги до Done>
**Blockers:** <что мешает + #N блокера, либо «нет»>
**Next session entry point:** <команда, файл или ссылка, с которых продолжать>
```

Четыре поля, все четыре, даже если поле пустое («нет»). Комментарий, а не правка
тела: тело — постановка, комментарии — история.

Следующая сессия читает последний stop-state **до** любых действий и трактует его
утверждения как **гипотезы**: сверяет с реальными issue/PR/ветками, расхождение
несёт владельцу (память `orient-before-acting`). Stop-state новее последнего
claim-комментария снимает claim-сигнал комментария; сигнал ворктри снимается
только `pnpm worktree:teardown <N>`.

## 6. Порог значимости: issue или строка в `DEBT.md`

Отдельная **issue** заводится, если долг попадает хотя бы под один пункт:

1. блокирует deliverable или лежит на его критическом пути;
2. виден пользователю либо это прод-риск (безопасность, данные, деньги);
3. должен быть сделан до ближайшего релиза/деплоя.

Всё остальное — **одна строка в `DEBT.md`**, добавляемая тем же коммитом или тем
же PR, что и работа, которая долг вскрыла. Правила самого файла (return condition
у каждой строки, обязательный sweep на `/wrap` и на закрытии эпика, запрет
«первого инцидента» как return condition для денег/вычислений и для единственного
пути редактирования сущности) остаются в `DEBT.md` и здесь не дублируются.

Порог применяется **в момент обнаружения** долга. Уже заведённые issue не
переоценивают и не «подчищают» этим правилом — только по явной просьбе владельца;
указание «разгрести бэклог» значит сделать, а не закрыть.

Промоция строки `DEBT.md` → issue идёт тем же путём, что любая задача: через
обёртку `issue:create`, с `source:*` (обычно `source:retro`), `kind:*` и
milestone; строка при этом отмечается ссылкой на созданную issue.

## 7. Тулинг (этап 2) — контракты, без реализации

- **`pnpm issue:create`** — единственный путь создания issue (сырой
  `gh issue create` запрещается): fail-closed валидация **до** любого gh-вызова
  (ровно один `source:*`, ровно один `kind:*`, непустой `--milestone`, непустое
  тело), затем создание + добавление на Project 2 + `Status=Todo` + деривация org
  Type из kind-лейбла + assignee `@me`; `--repo` запрещён (борд привязан к репо).
- **`pnpm board:status <issue> <Todo|In Progress|Done>`** — детерминированная
  установка статуса на борде одним targeted GraphQL-запросом; `Closes #N` колонку
  не двигает, это и есть самый забываемый шаг.
- **`pnpm pr:land <pr>`** — хвост закрытия PR одной командой: гейт → мерж →
  снятие своей PR-строки с борда → `Status=Done` каждой `Closes #N` → teardown
  ворктри → пересводка; первая упавшая стадия останавливает хвост.
- **`pnpm backlog:triage`** — отчёт готовности из **нативного** графа:
  takeable/blocked, field hygiene (source/kind/milestone/assignee), рёбра без
  rationale, mega-blockers (узел, блокирующий ≥5 задач), сверка обоих
  claim-сигналов (§4) с возрастом.
- **Скилл «issue-граф из спеки»** (адаптация ds `open-ears-issues` без EARS):
  родитель + дети нативными sub-issues, рёбра сразу, максимум одна берущаяся
  задача на выходе, номера issue дописываются в спеку.
- **`branch-protection.json`** — декларативный payload защиты `main` (required
  check, линейная история, запрет force-push и удаления, разрешение тредов);
  серверная активация — по факту доступности на нашем плане GitHub.
