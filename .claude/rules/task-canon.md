# Канон задачника — как формулируется задача

Задачник репо — **GitHub Issues** `bbm-academy-org/bbm-portal` (CLAUDE.md); Plane
`BBMP-*` — организационный слой, не этот канон. Правила ниже — перенос образца
ds-platform (инвентаризация #127) под наши лейблы, борд и `task-cycle`.

Действует **на новые issue**; существующие переоформляет задача 7.2, а не задним
числом. Канон описывает **формулирование**; жизненный цикл (план → «го» → TDD →
ревью → приёмка → мерж) остаётся за `.claude/skills/task-cycle/SKILL.md`, ветки и
порты — за `parallel-sessions.md`.
Язык: **заголовки секций и маркеры полей — английские и фиксированные** (их
парсит тулинг, §7), содержание — русское, как во всех наших issue.

<!-- решение автора: смешанный язык вместо целиком английского ds-шаблона — у нас

## 1. Тело issue — фиксированный скелет

```markdown
**Source:** <на основании чего задача существует — свободный текст>

## Context

<Почему сейчас. Какую проблему закрывает. Ссылки: спека `docs/specs/…`,
ADR `docs/adr/…`, PRD, комментарий владельца с датой.>

## Scope

**In scope:**

- <конкретный deliverable>

**Out of scope:**

- <что задача НЕ закрывает и куда это уходит>

## Spec reference

<Спека/ADR + конкретный §. Если спека не нужна по gate'у task-cycle stage 1a —
пишется «нет спеки: <причина>», пустым это поле не бывает.>

## Acceptance criteria

- [ ] <наблюдаемо и проверяемо: команда, URL, статус, файл>

## Dependencies

**Blocked by:** #N — <технический rationale одной строкой>
**Blocks:** #M

## Notes

<Свободный текст. Сюда же сессии постят stop-state-комментарии (§5).>
```

Уровень заголовка не значим: `pnpm issue:create` пишет `##`, а issue-формы
GitHub (`.github/ISSUE_TEMPLATE/*.yml`) рендерят свои поля как `###`. Тулинг
читает обе формы; переписывать тело задачи ради уровня решётки не нужно.

Семантика и обязательность:

| Секция                | Что в ней                                                                                                                     | Обязательна          |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| `**Source:**`         | **на основании чего** задача существует — свободный текст (§2). Не путать с `channel:*`-лейблом: тот про «кто завёл в трекер» | всегда               |
| `Context`             | почему сейчас, какую боль закрывает, откуда взялось решение                                                                   | всегда               |
| `Scope`               | **In** — deliverable'ы; **Out** — явно исключённое с адресом («уходит в #M»). Пустой Out — запах: значит границы не думали    | всегда               |
| `Spec reference`      | спека/ADR/§ либо явное «нет спеки: …». Это фиксация gate'а stage 1a, а не украшение                                           | всегда               |
| `Acceptance criteria` | чек-лист наблюдаемых фактов. «Работает» — не критерий; критерий — что открыть/запустить и что увидеть                         | всегда, кроме `epic` |
| `Dependencies`        | человекочитаемое зеркало **нативного** графа (§3) + rationale ребра                                                           | если граф непуст     |
| `Notes`               | остальное; stop-state-комментарии живут комментариями, не правкой тела                                                        | по необходимости     |

Строка **`**Source:**` — обязательный свободный текст**, и она отвечает на
вопрос «почему эта задача вообще существует», а не «кто её завёл». Примеры:

- `баг-репорт Антона в Mattermost 2026-08-04`
- `executive-решение партнёров от 2026-07-30`
- `просьба коллеги на созвоне по контенту`
- `сам поймал при работе над #124`
- `ретро сессии 2026-08-01`
- `обновилась зависимость payload 3.86`
- `изменилась миссия — PRD §2 переписан`

Списком это не задать: пространство источников открытое, и именно этот контекст
теряется первым. Строку ставит `pnpm issue:create --source "<текст>"` (руками её
в тело не пишут — тогда источников правды стало бы два); из веб-интерфейса её
заполняет обязательное поле формы.

У задачи типа **Bug** секция `Context` содержит воспроизведение: окружение, шаги,
ожидалось/получилось — иначе задача не берётся, а возвращается автору (форма
`.github/ISSUE_TEMPLATE/fix.yml` подставляет эти поля сама).
Для `epic` `Acceptance criteria` заменяется составом sub-issues: критерий эпика —
закрытые дети, отдельного чек-листа он не заводит.

**Заголовок** — свободный русский текст без Conventional-Commits-префикса: класс
задачи несёт штатное поле **Type**, дублировать его в title незачем.

## 2. Таксономия: Type (штатный) + ровно один `channel:*` + milestone

**Ровно один штатный `Type`** — `Bug` · `Feature` · `Task`. Это классификатор
задачи, и он живёт в поле GitHub, а не в лейбле: типы заведены в организации,
показываются в сайдбаре issue и фильтруются наравне с milestone и assignee.

<!-- решение владельца, 2026-08-04: «не надо выдумывать новые поля взамен
существующих». Отсюда: класс задачи — штатный Type, а не kind:*-лейблы (которые
были в проекте канона по образцу ds-platform). Кастомный лейбл остаётся ровно
там, где штатного поля нет вовсе — это `channel:*` -->

**Происхождение задачи — два разных измерения, и путать их дорого:**

| Измерение                 | Отвечает на вопрос                    | Где живёт                   | Форма                 |
| ------------------------- | ------------------------------------- | --------------------------- | --------------------- |
| **Source** (§1)           | на основании ЧЕГО задача существует   | строка `**Source:**` в теле | свободный текст       |
| **Channel** (`channel:*`) | КАК она попала в бэклог, кто её завёл | лейбл                       | ровно один из четырёх |

**Ровно один `channel:*`** — канал попадания в трекер: `channel:owner` (завёл
или запросил владелец), `channel:spec` (открыта механически из спеки/ADR —
issue-граф), `channel:retro` (ретро, `/wrap`, разбор инцидента), `channel:agent`
(инициатива агента — самая частая причина мусора в бэклоге, поэтому маркируется
явно). Список закрыт и служит порядку, а не аналитике: штатного поля под канал у
GitHub нет, это единственная кастомная таксономия репо. Лейблы заводит
`pnpm taxonomy:bootstrap --apply`.

<!-- решение владельца, 2026-08-04: прежняя таксономия `source:*` совмещала оба
измерения в одном лейбле и вырождалась — «99% задач будут запрошены оунером,
пользы никакой». Настоящий источник контекстуален и на уровень выше: баг-репорт
от юзера, executive-решение партнёров, просьба коллеги, сам поймал проблему,
обновилось приложение, изменилась миссия. Enum'ом это не выразить — отсюда
обязательный свободный текст в §1. Деление owner/spec/retro/agent владелец при
этом оставил («всё равно нужно для порядка»), но уже как отдельное поле-канал -->

Обязательны оба: задача без канала не создаётся, задача с пустым Source — тоже.

Цепочка одна и без таблиц перевода, первичен Type: **Feature** → ветка
`feat/<N>-<slug>` → коммит `feat: …`; **Bug** → `fix/…`; **Task** → `chore/…`.
Префикс ветки выводит `pnpm task:worktree <N>` из Type задачи. Для
docs-only изменения ветку можно назвать `docs/<N>-<slug>` вручную: отдельного
org-типа Docs нет и заводить его незачем — тип задачи при этом остаётся `Task`.

**Milestone обязателен.** Milestone — долгоживущая тема, не спека и не эпик.
Продуктовая тема сейчас одна — «Консолидация платформы»; постоянный fallback
**«Платформа: эксплуатация и упрочнение»** для процессных/эксплуатационных
задач, не попадающих ни в одну тему, заводит `pnpm taxonomy:bootstrap --apply`
(он же заводит лейблы `channel:*`). Задача без milestone не создаётся.

**Структурные лейблы** (ортогональны таксономии, не заменяют её): `epic` —
зонтичная issue; `consolidation` — тематическая метка эпика консолидации,
уходит вместе с закрытием milestone. Эпик тоже несёт свой Type, свой канал и
свою строку Source — по классу своего deliverable.

**Запрещённый класс лейблов — статусные** (`blocked`, `ready`, `in progress`).
Статус берётся из нативного графа и борда; лейбл был бы вторым источником правды,
который рассинхронизируется первым.

**Судьба дефолтных лейблов GitHub.** Миграцию выполняет задача 7.2 одним
проходом вместе с переоформлением задач, которые их носят; до неё
`pnpm backlog:triage` показывает носителей в секции «Гигиена полей».

| Лейбл                                              | Судьба                                                                                                      |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `bug` (3), `enhancement` (11), `documentation` (3) | задачи получают Type `Bug` / `Feature` / `Task`, лейблы удаляются — иначе два имени для одного класса       |
| `duplicate`, `invalid`, `wontfix`                  | удаляются: это причины закрытия, а не свойства задачи (`gh issue close --reason not planned` + комментарий) |
| `good first issue`, `help wanted`                  | удаляются: приватное репо с одним владельцем и агентами, внешних контрибьюторов нет                         |
| `question`                                         | удаляется: вопрос владельцу — это не задача бэклога                                                         |

Assignee по умолчанию `@me` — отметка того, кто задачу завёл, а не распределение
и **не** сигнал занятости: сигналы claim'а ровно два и оба в §4 (ворктри и
статус борда). Обёртка проставляет его каждой новой задаче, поэтому строка
«нет assignee» в `backlog:triage` срабатывает только на задачах, заведённых до
канона, — что и нужно задаче 7.2.

## 3. Канон связей — нативный граф, не проза

**Иерархия и зависимости живут в API GitHub, а не в тексте.** Проза «часть #117»,
«зависит от #130» связью **не считается** — её не видит ни борд, ни triage.

- **Родитель → ребёнок** — нативный sub-issue:
  `gh api --method POST repos/$OWNER/$REPO/issues/<P>/sub_issues -F sub_issue_id=<db-id ребёнка>`
  (эндпоинты берут **numeric DB id**, не номер: `gh api repos/$OWNER/$REPO/issues/<n> --jq .id`).
- **Зависимость** — `blocked_by`:
  `gh api --method POST repos/$OWNER/$REPO/issues/<B>/dependencies/blocked_by -F issue_id=<db-id блокера>`.
  Обратное ребро GitHub выводит сам — второй раз в другую сторону не проводить.
- Секция `Dependencies` в теле — **зеркало** графа для человека; расходится с
  графом — прав граф, тело правится.

**`blocked_by` = только техническая зависимость, с записанным rationale.** Ребро
значит «раньше физически нельзя», а не «сначала хотим другое»: приоритет
выражается порядком на борде и волнами хендоффов, никогда не рёбрами. Rationale
пишется **строкой в `Dependencies` заблокированной задачи** (`#N — почему`);
допустим комментарий на любой из двух задач, если контекст длиннее строки. Ребро
без rationale — provenance-orphan: triage его помечает, и это повод оспорить
ребро, а не считать фактом.

**Никогда не блокеры:** родитель/эпик, «связано с», «преемник», «сначала
обсудить». Иерархия ≠ зависимость.

**Открытие набора задач из спеки:** каждый ребёнок — нативный sub-issue родителя,
рёбра между детьми расставляются сразу, номера созданных issue дописываются
обратно в спеку. Набор не может приземлиться как N одновременно берущихся задач:
берущаяся — одна, голова критического пути, остальные заводятся заблокированными.
Кросс-репные дети (`bbm-public-website`) линкуются нативно (одна организация), но
**заводятся, а не реализуются** здесь — граница из CLAUDE.md.

## 4. Claim — задача взята = ворктри **И** статус

Спека консолидации §3, п. 10: сигналов занятости **два, обязательны оба**:

1. **ворктри** `.claude/worktrees/<N>` со своей веткой `<type>/<N>-<slug>`
   (`pnpm task:worktree <N>`) — создаётся **до первой правки файла**;
2. **статус `In Progress`** на борде Project 2 — ставится тем же движением.

Расхождение — само по себе нарушение канона, а не «мелочь»; его ловит
`pnpm backlog:triage` (секция «Расхождения claim»). Разрешение асимметрично:

- **ворктри есть, статуса нет** → правды больше у ворктри: работа физически идёт,
  борд отстал → **чинится борд**. Ворктри и ветка — факт файловой системы и
  origin, их нельзя «забыть по невнимательности» в обратную сторону.
- **статус есть, ворктри и ветки нет** → задача **не становится свободной
  автоматически**: агент помечает claim как протухший (с возрастом), решение
  освободить принимает лид/владелец. Чужой claim снимается людьми, не скриптом.

<!-- решение автора: SSOT-правило асимметрично — «ворктри как свидетельство
работы» + «борд как право взять» — потому что симметричное «побеждает свежий
сигнал» разрешало бы скрипту отбирать задачу у живой чужой сессии, а это ровно
класс инцидентов из parallel-sessions.md -->

Выбранный порт dev-стенда фиксируется комментарием в issue (правило
`parallel-sessions.md`) — это часть того же claim'а: владелец открывает ссылку,
соседняя сессия видит занятый слот.

## 5. Stop-state-комментарий — фиксированная форма

Сессия, останавливающаяся на **не закрытой** задаче (конец сессии, блокер,
переключение приоритета), обязана оставить комментарий ровно такой формы:

```markdown
**Where I stopped:** <последний коммит / последняя успешная команда / где чтение оборвалось>
**What remains:** <конкретные шаги до Done>
**Blockers:** <что мешает + #N блокера, либо «нет»>
**Next session entry point:** <команда, файл или ссылка, с которых продолжать>
```

Четыре поля, все четыре, даже если поле пустое («нет»). Комментарий, а не правка
тела: тело — постановка, комментарии — история.

Следующая сессия читает последний stop-state **до** любых действий и трактует его
утверждения как **гипотезы**: сверяет с реальными issue/PR/ветками, расхождение
несёт владельцу (память `orient-before-acting`). Stop-state новее последнего
claim-комментария снимает claim-сигнал комментария; сигнал ворктри снимается
только `pnpm worktree:teardown <N>`.

## 6. Порог значимости: issue или строка в `DEBT.md`

Отдельная **issue** заводится, если долг попадает хотя бы под один пункт:

1. блокирует deliverable или лежит на его критическом пути;
2. виден пользователю либо это прод-риск (безопасность, данные, деньги);
3. должен быть сделан до ближайшего релиза/деплоя.

Всё остальное — **одна строка в `DEBT.md`**, добавляемая тем же коммитом или тем
же PR, что и работа, которая долг вскрыла. Правила самого файла (return condition
у каждой строки, обязательный sweep на `/wrap` и на закрытии эпика, запрет
«первого инцидента» как return condition для денег/вычислений и для единственного
пути редактирования сущности) остаются в `DEBT.md` и здесь не дублируются.

Порог применяется **в момент обнаружения** долга. Уже заведённые issue не
переоценивают и не «подчищают» этим правилом — только по явной просьбе владельца;
указание «разгрести бэклог» значит сделать, а не закрыть.

Промоция строки `DEBT.md` → issue идёт тем же путём, что любая задача: через
обёртку `issue:create`, с Type, каналом (обычно `--channel retro`), строкой
Source («ретро сессии <дата>») и milestone;
строка при этом отмечается ссылкой на созданную issue.

## 7. Тулинг

Канон называет команду и её роль; контракт каждой — в самом артефакте (`--help`
скрипта и шапка файла).

| Команда / артефакт                             | Роль в каноне                                                                                          | Где контракт                               |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------ |
| `pnpm issue:create`                            | **единственный** путь создания задачи; сырой `gh issue create` запрещён                                | `tools/gh/create-issue.mjs` (`--help`)     |
| `pnpm board:status <issue> <статус>`           | половина claim'а (§4) и `Done` после мержа: `Closes #N` колонку борда не двигает                       | `tools/gh/set-board-status.mjs`            |
| `pnpm pr:land <pr>`                            | хвост закрытия PR одной командой; первая упавшая стадия останавливает хвост                            | `tools/gh/pr-land.mjs`                     |
| `pnpm backlog:triage`                          | готовность из нативного графа, гигиена полей, рёбра без rationale, мега-блокеры, сверка claim-сигналов | `tools/gh/backlog-triage.mjs`              |
| `pnpm taxonomy:bootstrap [--apply]`            | заводит `channel:*`-лейблы и fallback-milestone; ничего не удаляет                                     | `tools/gh/bootstrap-taxonomy.mjs`          |
| `pnpm task:worktree <N>` / `worktree:teardown` | ворктри как первый claim-сигнал (§4); префикс ветки выводится из Type                                  | `parallel-sessions.md`                     |
| Скилл `spec-issue-graph`                       | открытие связного набора задач из спеки: sub-issues, рёбра, одна берущаяся                             | `.claude/skills/spec-issue-graph/SKILL.md` |
| Формы задач                                    | путь владельца из веб-интерфейса; форма сама ставит Type и `channel:owner`, пустая issue запрещена     | `.github/ISSUE_TEMPLATE/*.yml`             |
| `.github/branch-protection.json`               | декларативная защита `main`: required check `lint-and-typecheck`, линейная история, запрет force-push  | сам файл                                   |

`.github/branch-protection.json` — payload, а не состояние: применяется вручную
`gh api --method PUT repos/bbm-academy-org/bbm-portal/branches/main/protection --input .github/branch-protection.json`,
и на текущем плане GitHub может не примениться вовсе.

**Ревью серверной защитой не требуется, но требуется гейтом.** Обязательное
APPROVE-ревью в payload не включено: единственный человек с правами — автор PR,
сам себе APPROVE он поставить не может. Проверяемая форма ревью у нас другая —
комментарий субагента-ревьюера со строкой `VERDICT: APPROVE`, и `pnpm pr:land`

обязательна и печатается. Приёмка владельца (stage 5) гейтом не проверяется:
о ней печатается напоминание на каждом прогоне.
