**Unit & states.** One element class with five forms (spec 584 F1–F5) plus the figure unit:

- *KPI figure / tile* (F2) — label (sentence case) · value (proportional figures, semibold) · marks row (chips: «предварительно», «по курсу ЦБ на <date>», «частично по курсу ЦБ · <sum>», «по себестоимости») · optional sub-line. Exactly one hero figure per view (remaining).
- *Glass* (F1) — plan (limit) vs fact (spent), share used, remaining; overflow state (fill past the limit marker, remaining negative, «лимит исчерпан») — never clipped; `role="meter"` with `aria-valuenow`.
- *Monthly columns* (F3) — gross + net per month, negatives below the zero line, current/first partial month hatched + «неполный», trailing-average levels over exactly the N averaged months, labelled at the right edge.
- *Waterline* (F4) — cumulative net line with area wash to zero, cumulative contributions as a step line, zero baseline, −limit reference level; one note (income note in `B`, rate note in another `D`).
- *Ranked bar list* (F5) — label · bar · value · share · chevron; «курсовой результат» line last and visually de-emphasised; rows open the settled data-table block in a Sheet.
- States every form must hold: **loading** (Skeleton of the same geometry — kit `@/ui/skeleton`), **empty ledger** («С <starts_on> операций нет», zero figures, axes drawn), **no budget** («Бюджет не задан», no charts), **partial data** (incomplete months hatched), **withheld** (no number; the causing currencies named; a withheld month draws no column and breaks the cumulative line from that month — never a partial sum), **provisional** (chip on the figure, column/point/line from that month on), **fallback-labelled** (item mark / aggregate mark «частично по курсу ЦБ» with the sum; on charts a small ring marker on the month + legend note), **mixed actual/CBR aggregates**, **B vs other-currency view** (rate line + the EARS-722 item 4 difference lines, shape of charts unchanged, units change), **narrow width** (tiers stack to one column; chart axes thin their ticks).

**Best-practice rule + citations** (pages fetched 2026-11-25):

- NN/g, *Dashboards: Making Charts and Graphs Easier to Understand* — https://www.nngroup.com/articles/dashboards-preattentive/ : use position/length (bars, lines) over angle/area; **avoid radial gauges, prefer linear bullet charts that show a value against a target**; sort bars; never colour alone for categories. → the glass is a linear bullet/fill, not a radial (rules out shadcn `chart-radial-*` blocks for F1), F5 sorted by value.
- IBM Carbon, *Dashboards* — https://carbondesignsystem.com/data-visualization/dashboards/ : most important data highest contrast + largest area, top-left F-pattern; **same colour for each data set across the whole dashboard**; consistent legend position. → spent/gross keeps one colour in F1, F3, F5; contributions one other colour everywhere.
- Carbon, *Simple charts* — https://carbondesignsystem.com/data-visualization/simple-charts/ : step line for values that change at intervals (→ cumulative contributions as a step line); area = line with filled region.
- GitHub Primer, *Data visualization* — https://primer.style/product/ui-patterns/data-visualization/ : marks ≥3:1 and text ≥4.5:1 against the surface; never colour alone; lines 2px, the second line in a different stroke style; omit the legend for one series, show it for >1; line ≤5 series, bar ≤10 bars for comparisons; a table/preview of the data for most charts.
- UK Government Analysis Function, *Data visualisation: charts* — https://analysisfunction.civilservice.gov.uk/policy-store/data-visualisation-charts/ : bar axis starts at zero, never broken; rank bars unless ordered; **include reference points such as targets or averages** (→ −limit level, trailing averages); **avoid dual axes**; line charts for time series; every chart needs a text alternative (table or description). GOV.UK Design System itself (https://design-system.service.gov.uk/patterns/) has no chart component — negative result.
- Adobe React-Aria, *Meter* — https://react-aria.adobe.com/Meter : a meter is a quantity within a known range, with a label and a value label → the glass carries `role="meter"`, `aria-valuemin/max/now` and an `aria-valuetext` with plan and fact.
- shadcn/ui *Chart* docs — https://ui.shadcn.com/docs/components/chart : built on **Recharts v3**, you compose Recharts directly; `ChartContainer` needs a height/aspect class; `ChartConfig` maps keys → labels/colours (`var(--chart-N)`, with a `theme: {light, dark}` form); `ChartTooltip`/`ChartLegend`; `accessibilityLayer` adds keyboard and screen-reader support.
- dataviz method (skill, local): one axis; 2px lines; ≤24px columns with 4px rounded data-end; 2px surface gap; recessive hairline grid; selective direct labels; text in text tokens, not series colour; status colours reserved; palette validated by script — results below.

*Treemap breakdown (F5 as picked) — design and rationale* (pages fetched 2026-11-25):

- NN/g, *Treemaps: Data Visualization of Complex Hierarchies* — https://www.nngroup.com/articles/treemaps/ : treemaps are good at spotting large contributors at a glance (the owner's «сразу оценить масштаб»), but «not suited for tasks involving precise comparisons» — «a bar chart would communicate this information more accurately»; small items become «a sea of tiny rectangles, many too small to bear a text label»; area cannot be negative; use «a secondary signal (such as text within the rectangle or appearing on hover)» for colour-blind users; high-contrast labels, a distinct selected state, detail overlays.
- IBM Carbon, *Spatial charts* — https://carbondesignsystem.com/data-visualization/spatial-charts/ : tree maps «can work for visualizing a part-to-whole relationship among a large number of categories», «as long as … exact comparisons between the categories is not a primary concern».
- → **The treemap answers «what is big»; B's ranked bar rows, kept unchanged beneath it, answer «exactly how much».** Owner correction (2026-11-25): B's horizontal-bar rows are NOT replaced — the same rows as option B (name + marks · bar · amount · share · chevron), each bar now in its tile's colour (neutral for the uncoloured items, hatched for «курсовой результат»). The rows are links: the keyboard and screen-reader path, and they open the same drill-down. The SVG is one `role="img"` whose label names every item with its share and points to the rows; tiles are mouse targets only. Primer / Analysis Function's «text alternative for every chart» rule (cited above) is met by the rows.
- **Tile labels degrade in three tiers** by measured text width: name · amount · share (+ mark chip when tall enough) → name · share → no label (tooltip + rows carry it). Names are ellipsised to the tile width, never overflow. A mark that does not fit becomes `*` on the tile, explained in the footer line. Hover: tooltip (name, amount, share, marks) + a 2px ring, and the bar row highlights; hovering/focusing a row rings its tile. Click on a tile or row → the drill-down Sheet (settled `data-table` block), same as a B row. Mark chips on tiles use the page's mark tokens (provisional: `--mark-provisional` / `-foreground`; CBR: card chip with `--foreground`).
- **Kept from B:** the projects / categories / counterparties tabs; «курсовой результат» as its own tile (hatched neutral, last row behind B's rule, hatched bar); «предварительно» and, in $, «по курсу ЦБ» / «частично по курсу ЦБ» marks on tile, tooltip and row; the footer «Строки, включая курсовой результат, складываются в потрачено за период: <sum>». A **negative** FX result (possible in a real ledger) cannot be an area: it stays in the rows and the total, with a one-line note under the map.
- **Colour — validated, and the reason it is three hues, not six.** A treemap is an all-pairs form (any two tiles may touch, depending on the data). `validate_palette.js --pairs all` on C's six slots **FAILS** in both modes (light: protan ΔE 3.6 green↔orange, normal-vision 12.4 amber↔orange; dark: deutan ΔE 0.4 pink↔aqua). The skill's rule for all-pairs forms is the series cap (≤3 hues), not a re-step. From C's palette: **blue / teal / amber**; C's **orange is deliberately skipped** (in B it already means «взносы»). Owner correction (2026-11-25): dark text on blue/teal was unreadable → tile label ink is chosen by measured WCAG contrast between two ink tokens (light ink whenever it reaches 4.5:1), and blue/teal were re-stepped darker so WHITE text passes AA: light `--chart-7` = B's gross blue oklch(0.55 0.162 255.8), `--chart-8` teal oklch(0.534 0.105 170.5) (C's aqua at lower L), `--chart-9` amber oklch(0.779 0.164 75.9); dark `--chart-7` oklch(0.511 0.158 256.4), `--chart-8` same teal, `--chart-9` oklch(0.698 0.146 74.8). Re-validated all-pairs: light PASS (CVD ΔE 17.8, normal 18.6, chroma ≥0.1; contrast WARN amber 2.05:1 → relieved by in-tile labels + rows), dark vs card `#171717` all PASS (CVD 14.0, normal 18.5, all ≥3:1). Other items: one neutral step `--chart-10`; FX: hatched `--chart-11` over `--muted`.
- **Measured label contrast** (every tile × theme, computed in the rendered page by a Playwright audit: for every treemap tile it reads the tile fill (for the hatched FX tile, both the `--muted` ground and the 55 % hatch mix, taking the worse) and every label's fill, and computes the WCAG 2 relative-luminance ratio; re-run 2026-11-25 on the vendored `BudgetDashboard.html` in RUB and USD, light and dark, at 1280 px and 390 px with identical results; name, amount and share use the same ink, the share is no longer faded): light — blue 4.71, teal 4.71 (white ink), amber 9.64, neutrals 13.36, FX hatch worst pixel 11.71 (dark ink); dark — blue 5.57, teal 4.71 (white), amber 7.18 (dark), neutrals 9.93, FX 7.73 (white). Chips: «предварительно» 6.76 light / 8.78 dark; CBR chips 19.80 / 17.18. All ≥4.5:1 (AA) for name/amount, so the 3:1 floor for the share is exceeded too.
- **Colour follows the entity:** the three hue slots belong to the three largest items over the budget's lifetime per dimension (stable), not to the current rank under a period filter — so a period change never repaints a category. Stage-B parameter: whether a category registry should pin slots explicitly instead.
- Tile 1 and the gross-burn series share one hue (`--chart-7` = `--chart-1` in light; one step darker in dark, for white labels). Intended — both mean «spent money».

*Implementation (Recharts finding).* Recharts 3.x `Treemap` (docs fetched https://recharts.github.io/en-US/api/Treemap/ and the example https://recharts.github.io/en-US/examples/CustomContentTreemap/) supports custom tile rendering through `content` (an element or a function receiving `x, y, width, height, depth, index, name, root …`; SVG only — no HTML inside), `dataKey` / `nameKey`, `aspectRatio` (squarified, default golden ratio), `isAnimationActive` (respects reduced motion), `type="flat"|"nest"`. Source at tag `v3.8.0` (`src/chart/Treemap.tsx`) confirms an `onClick(node)` prop on leaf nodes, Tooltip support (`defaultTooltipEventType: 'item'`), and `@consumes ResponsiveContainerContext` — so it sizes inside shadcn's `ChartContainer`, which renders `<div data-slot="chart">` + `ChartStyle` + Recharts `ResponsiveContainer` (fetched `ui.shadcn.com/r/styles/new-york-v4/chart.json`, `recharts@3.8.0`). `ChartTooltipContent` reads `item.name` / `item.payload.fill`, so the tile fill can come from `ChartConfig` (`var(--color-<key>)`). Not provided: `accessibilityLayer` / keyboard on treemap tiles — hence the bar rows carries keyboard and screen-reader access. Build in #586: `BreakdownTreemap.tsx` (`'use client'`, `<ChartContainer><Treemap data content={<Tile/>} onClick isAnimationActive={false}/></ChartContainer>`, `<Tile>` does the three-tier labels) + `BreakdownList.tsx` (B's bar rows as links, kit `Tabs`); colours from the token block below. No alternative engine needed.
